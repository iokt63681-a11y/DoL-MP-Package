# 联机同步修复：同步事件，不是同步 1/2/3

## 一、根因

### 1. 选项投票按 passage 分桶，事件错开后永远不同步

`server.js` 的 `handleLinkVote` 用 `passage` 作为 `linkVotes` 的 key：

```js
const passage = text(msg.passage || client.passage, 120);
...
let bucket = room.linkVotes.get(passage);
```

`groupedPeersInPassage` 也只找"同一个 passage 上的队友"。所以：

- A 在事件 X，B 在事件 Y；
- A 的投票进 X 桶，B 的投票进 Y 桶；
- 每个桶都只看到自己一个人，`peers.length <= 1`，直接 `immediate` 提交；
- 两边各走各的，事件就这样错开了。

### 2. 客户端在 `linkKey` 找不到时，回退到 `linkIndex`

```js
if (!targetEl) targetEl = links[msg.linkIndex];
```

两边的 DOM 链接顺序只要有一点不同（条件链接、代词、事件上下文），`linkIndex` 就会点到另一个选项。这正是"同步的是 1/2/3，不是事件"的直接来源。

### 3. `event_trigger` 没有事件身份和 PRNG

`onPassageDisplay` 只发：

```js
send({ t: "event_trigger", passage, phase, eventContext, priority, inCombat });
```

`resolveEventArbitration` 收到后：

- 用 `room.prng = genPrngPack()` 生成一个**新的随机种子**；
- 只发 `sync_jump`，不带事件名/内容。

结果：B 跳到同一个 passage，但事件池用新种子重新抽了一次，抽到的事件不一定是 A 的那个。

### 4. `event_pick` 和 `event_trigger` 抢同一件事

`runeventpool` 抽到事件后，`onEventPicked` 会发 `event_pick`（带 name/content/prng），`onPassageDisplay` 又会发 `event_trigger`（不带内容）。两个 220ms 仲裁器同时跑：

- `event_pick` 先到：`sync_event` 先让 B 进入正确事件；随后 `sync_jump` 再 `enginePlay`，`eventPoolOverride` 已经被消费，B 又重抽一次；
- `event_trigger` 先到：B 先重抽一个错事件，`sync_event` 再覆盖，出现闪回/错页。

### 5. `link_commit` 在 passage 不一致时被直接忽略

```js
case "link_commit":
  if (State.passage === msg.passage) executeCommittedLink(msg);
  break;
```

B 如果还停在上一页/另一个事件，收到 commit 什么都不做，于是永远落后。

## 二、修复

### 1. 引入 `eventKey`

客户端 `currentEventKey()`：

```
passage + "#" + phase + "#" + (lastEventPick.name || eventPoolOverride || "")
```

事件身份 = 地点 + 阶段 + 事件名。两边同一个事件才会得到同一个 key。

- `event_trigger` / `event_pick` / `link_vote` / `link_commit` / `sync_jump` / `sync_event` 全部带 `eventKey`；
- 服务端 `room.currentEventKey` 记录当前全队事件；
- 投票的 `eventKey` 和 `room.currentEventKey` 不一致时，服务端给该客户端发 `event_resync`，不把票投进桶里。

### 2. `event_pick` 优先，`event_trigger` 让路

- `handleEventTrigger`：如果该客户端的 `event_pick` 还在 pending，直接忽略 trigger；
- `resolveEventArbitration`：如果 `eventPickPending` 非空，直接返回，让 `event_pick` 裁决；
- `resolveEventArbitration` 使用 `winner.prng`，不再用新的随机种子；
- `resolveEventPick` / `resolveEventArbitration` 都会写 `room.currentEventKey` / `currentEventPassage` / `currentEventName` / `currentEventContent` / `currentPrng`。

### 3. 去掉 `linkIndex` 兜底

`executeCommittedLink` 找不到 `linkKey` 时：

- 有 `targetPassage` 就直接 `enginePlay(targetPassage)`；
- 没有就发 `event_resync`，让服务端把当前事件重新同步过来；
- **不再点 `links[msg.linkIndex]`**。

### 4. 落后的客户端也能跟上

`link_commit` 在 `State.passage !== msg.passage` 时：

- 有 `targetPassage` 就跳到目标；
- 没有就发 `event_resync`。

`sync_jump` / `sync_event`：

- 记录 `S.currentEventKey`；
- `sync_jump` 如果带 `name/content`，写入 `eventPoolOverride`，再 `enginePlay`；
- `forceEvent` 时即使当前 passage 相同也重绘，确保事件上下文一致。

### 5. 新增 `event_resync`

服务端收到后，把当前 `currentEventPassage` / `currentEventKey` / `currentEventName` / `currentEventContent` / `currentPrng` 重新发给该客户端：

- `sync_jump`（forceEvent）
- 如果有事件内容，再发 `sync_event`

## 三、验证

- `node --check sync_patch/mp.js`：通过（exit 0）
- `node --check sync_patch/server.js`：通过（exit 0）
- patched server 在 8791 启动：正常监听，无 stderr
- 事件 key 引用 25 处；diff：`mp.js +36/-2`，`server.js +56/-1`

## 四、还需要实测

这是同步层改动，静态检查只能证明不报错，**必须双开实测**：

1. 两边进同一房间，开组队同步；
2. A 触发随机事件，确认 B 跳到**同一个事件名/passage**，不是同 passage 的另一个事件；
3. A 选 1，B 选 2，确认两边落到同一个 `linkKey` 目标；
4. A 先选，B 还没加载完，确认 B 被 `event_resync` 拉回同一事件；
5. 事件结束后再走一段，确认没有闪回/重复事件。

如果还有错开，抓两边 console 里的 `eventKey` / `passage` / `linkKey` 和 server 的 `currentEventKey`。

## 五、选项提议制（第二轮）

### 之前的问题

- 第一次点击就投票，第二次点同一个选项 `force:true`，服务端立刻 `immediate` 提交；
- 其他队友只看到"谁投了哪个"，没有"同意/不同意"的入口；
- 房主点地图移动时，服务端 `host_move` 直接 `sync_jump`，队友被强行拉走，没有提示；
- 不同地点也会被强行同步。

### 现在

1. **第一次点击 = 提议**，不再有第二次点击强制。
2. 同 passage 的队友在页面顶部看到：
   `A 提议：<选项> [同意] [不同意]`
   - 同意：按同一个 `linkKey` 投票；全员同意才 `link_commit`；
   - 不同意：发 `link_disagree`，服务端广播 `link_cancel`，本次不同步。
3. 服务端不再在分歧时随机 `link_commit`；分歧/超时都 `link_cancel`，不强行移动。
4. `host_move` 改成 `host_moved` 提示："房主去了 X，先汇合再同步"，不再 `sync_jump`。
5. 只有同一个 passage 上的队友才会进入投票桶；不同地点只做本地移动。
6. `link_commit` 在客户端 passage 不一致时，跳到 `targetPassage` 或 `event_resync`，不会按索引点错选项。

### 双开测试步骤

1. 两人同一 passage、开组队同步；
2. A 点选项 → B 顶部出现"同意/不同意"；
3. B 点同意 → 两边进入同一个 `targetPassage`；
4. 重来，B 点不同意 → 两边都不动，提示"本次同步取消"；
5. 房主点地图去别处 → 队友不被强拉，只看到"房主去了 X，先汇合再同步"；
6. 事件池事件 → 两边事件名和 passage 一致。

## 六、已知限制

- 非事件池事件（没有 name/content）的 `sync_jump` 只能同步 passage，不能保证内部随机分支一致；这类事件需要后续补 `eventContext` 快照。
- 联机双方 mod 版本/事件池不一致时，`eventKey` 会对不上，触发 `event_resync`；这是预期行为，但会多一次跳转。
- 没有改动战斗同步、PvP、交易、房间逻辑。
